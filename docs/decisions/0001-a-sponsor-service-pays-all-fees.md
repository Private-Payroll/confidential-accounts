# 1. A sponsor service pays all transaction fees

## Decision

Customers never hold NIGHT and never see a token. A sponsor service we operate pays the DUST cost of every transaction, using the protocol's two-phase balancing.

## Why

DUST is generated by holding NIGHT, at five DUST per NIGHT reaching capacity over a week, and it is non-transferable. It cannot be topped up into an account, and a shared account is not a person, so there is no wallet to fund.

Midnight supports this directly. Transaction balancing splits by token kind:

| Phase | Who | Call | Token kinds |
| --- | --- | --- | --- |
| 1 | Customer | `balanceUnboundTransaction` | `['shielded', 'unshielded']` |
| 2 | Sponsor | `balanceFinalizedTransaction` | `['dust']` |
| 3 | Sponsor | `submitTransaction` | |

The customer's wallet does not register for DUST generation at all.

Reference: `midnight-docs/static/midnight-wallet/snippets/dust-sponsorship.ts`.

## Consequences

- **The token kinds must not overlap.** Re-balancing a kind the other party already balanced is a double spend and the node rejects it. This is the failure mode to expect when the flow breaks.
- **Both parties set a TTL**, 15 to 30 minutes. A transaction that sits between phases expires.
- **The sponsor is the only component with spend authority.** It is modelled as the `FeeSponsor` interface in `src/midnight/ledger.ts` so it stays swappable for an HSM or a signing queue, and so it is the only thing that has to be audited for spend.
- **DUST capacity is an operational metric with a one-week refill curve.** Running dry fails every customer transaction at once. Alarm well before zero.
- **NIGHT holdings are a balance-sheet item** sized by transaction volume.
- **A sponsor that submits can censor.** Customers who object need a path to pay their own fees. The interface allows it; the default hides it.
